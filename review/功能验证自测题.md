# 功能验证自测题

功能验证岗自测题，覆盖 UVM 机制、SVA、覆盖率与验证方法学。适用方向标签：设计 / **验证** / 后端 / 架构。

#### 1. UVM 的 Factory 机制是什么？解决了什么问题？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）Factory（工厂）是 UVM 的对象创建代理——`type_id::create()` 代替 `new()` 创建对象；（2）通过注册表把"类型名"映射到构造器，支持运行时类型覆盖（override）——不改测试代码即可替换组件或激励；（3）`set_type_override_by_type` 做类型替换、`set_inst_override_by_type` 做实例级替换；（4）组件（uvm_component）必须经 factory 创建才能进入 UVM 的 phase 体系；事务类（uvm_object）创建方式灵活。

#### 2. UVM 的 Phase 机制怎么运转？为什么不能用 fork 手动建平台？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）Phase 把仿真生命周期划分为 build/connect/run/cleanup 等阶段，全部组件按固定顺序自动执行；（2）build_phase 自顶向下构造、connect_phase 自底向上连接——保证组件"先存在后连接"；（3）run_phase 与 12 个细分 task phase（reset/configure/main/shutdown）并行运行；（4）raise_objection/drop_objection 机制让 UVM 知道测试何时结束——不用 objection 挂起仿真，run 阶段会立即结束。

#### 3. uvm_config_db 怎么工作？set/get 的匹配规则？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）config_db 是 UVM 的配置数据库——set 方写入、get 方读取，通过层次路径 + 字段名匹配；（2）匹配规则：get 的路径是 set 路径的层次前缀即可命中（自顶向下传播），支持通配符 `*`；（3）set 必须发生在 build_phase 或更早，get 在 build_phase 中读取；（4）典型用途：传递 virtual interface 到 driver/monitor、传递配置对象、设置 verbosity。

#### 4. UVM 的 objection 机制是什么？测试怎么"结束"？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）仿真器不知道验证何时完成——objection 计数器是 UVM 与仿真器约定的"还有活没干完"信号；（2）sequence 开始时 raise_objection、结束时 drop_objection——计数归零且 run_phase 完成后仿真结束；（3）忘了 raise 的经典后果：仿真 0 时刻立即结束、什么都没跑；（4）多 sequence 并行时每个都独立 raise/drop，计数器共享。

#### 5. Sequence/Sequencer/Driver 怎么握手？get_next_item 和 item_done 什么关系？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）Sequence 是激励的"配方"、Sequencer 是调度器、Driver 是时序执行者——三者通过 TLM 握手解耦；（2）Driver 循环：`seq_item_port.get_next_item(req)` 取事务 → 按协议驱动引脚 → `item_done()` 通知完成；（3）get_next_item 阻塞等待 sequence 生成事务，item_done 告知 sequencer 可发下一个；（4）driver 侧可以 get_next_item 后立即 item_done（流水式）或驱动完再 item_done（背压式）——取决于是否需要反压。

#### 6. Virtual Interface 解决什么问题？为什么不能直接引用 interface？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）class 是动态对象，无法在类内直接引用静态的 interface——编译期层次不确定；（2）virtual interface 是指向 interface 实例的句柄，可在类内持有、在 config_db 中传递；（3）driver/monitor 通过 virtual interface 访问 DUT 引脚——平台与 DUT 的唯一物理连接点；（4）interface 内可封装 clocking block 与 modport，进一步隔离时序细节。

#### 7. UVM RAL（Register Model）前门访问和后门访问区别？

**适用方向**：验证　**出处**：[[verification/concepts/UVM方法学|UVM方法学]]

**要点**：（1）RAL 把寄存器抽象成对象模型，sequence 通过 read/write 访问寄存器，不直接写总线时序；（2）前门访问：经总线协议（AXI/APB 等）逐周期读写——真实但慢；（3）后门访问：通过层次引用（XMR）直接读写寄存器变量——零仿真时间但绕过协议逻辑，测不到总线路由正确性；（4）实践中前门做主路径验证、后门做配置注入与镜像检查（mirror/update）。

#### 8. 用 SVA 写一个"req 有效后 1-3 拍内 ack 有效"的断言

**适用方向**：验证　**出处**：[[verification/concepts/SVA断言|SVA断言]]

**要点**：（1）并发断言结构：`assert property (@(posedge clk) $rose(req) |-> ##[1:3] $rose(ack))`——|-> 是交叠蕴含、##[1:3] 是延迟范围、$rose 是上升沿检测；（2）可加 `disable iff (rst_n)` 复位期间暂停检查；（3）$rose 检测 0/X/Z 到 1 的跳变，比 `==1` 严格（只查沿不查电平）；（4）sequence 可命名复用，property 可带参数（如 req/ack 信号化）。

#### 9. 代码覆盖率和功能覆盖率有什么区别？覆盖不到怎么办？

**适用方向**：验证　**出处**：[[verification/concepts/覆盖率模型|覆盖率模型]]

**要点**：（1）代码覆盖率：行/分支/翻转/状态——工具自动统计"代码被执行过没有"，语义空白（执行过≠验证过）；（2）功能覆盖率：covergroup 采样设计关心的功能点（协议时序、边界值、交叉场景）——"该验证的行为验过没有"；（3）收敛流程：功能覆盖率是主要指标、代码覆盖率做参考（未覆盖行要人工审查是 dead code 还是遗漏）；（4）covergroup 要点：coverpoint bins、cross 交叉覆盖、采样时机（采样事件与数值稳定性）。

#### 10. 参考模型（Reference Model）怎么搭建？实时比对和离线比对怎么选？

**适用方向**：验证　**出处**：[[verification/concepts/验证平台架构|验证平台架构]]

**要点**：（1）参考模型用高层抽象（SystemVerilog class/C 模型）实现与 RTL 相同的功能——独立实现、不同实现细节，避免同源 bug；（2）实时比对：monitor 逐拍采样输出与参考模型比对——错误定位准但平台耦合紧、影响仿真速度；（3）离线比对：先跑 RTL 与参考模型各自输出结果文件（如 VCD/FSDB 比对），再离线 diff——解耦、可复用、定位到拍即可；（4）接口协议复杂或输出非确定（乱序）时用 scoreboard 先重整再比对。

#### 11. 形式验证和动态仿真各擅长什么？

**适用方向**：验证　**出处**：[[verification/concepts/形式验证|形式验证]]、[[verification/concepts/SVA断言|SVA断言]]

**要点**：（1）形式验证（Formal Verification）用数学方法穷举证明属性在所有可达状态下成立——不需要激励；（2）擅长：控制逻辑、协议一致性、死锁/活锁检查（死锁与活锁检测）、X 传播分析——动态仿真难穷举的状态空间；（3）动态仿真擅长数据通路、端到端场景、性能类验证——形式验证会状态爆炸；（4）主流分工：属性检查（Property Checking）做模块级形式验证 + 仿真做系统级。

#### 12. 约束随机验证怎么保证"有效激励"？约束冲突怎么办？

**适用方向**：验证　**出处**：[[verification/concepts/约束随机验证|约束随机验证]]

**要点**：（1）随机化让每次仿真探索不同状态组合，覆盖定向测试写不出来的边界场景；（2）约束（constraint）用声明式规则框定合法空间——inside/分布约束/蕴含约束/foreach；（3）约束冲突（constraint contradiction）导致随机化失败（randomize 返回 0）——用 `soft` 约束分层优先级，硬约束冲突才是真错误；（4）随机种子固定可复现——回归必须记录种子，bug 复现靠重放同种子。
