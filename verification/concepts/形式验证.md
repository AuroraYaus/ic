# 形式验证

形式验证（Formal Verification）是基于数学证明的验证方法，它使用形式化逻辑和算法来**穷举地证明**设计是否满足给定的属性规范，而不是通过样本测试（仿真）来推断。形式验证保证了给定属性在所有可能的输入组合和状态空间下都成立（或不成立，此时工具给出具体违反序列的一个反例（Counterexample））。形式验证不依赖测试激励——它从设计的状态空间出发，通过数学推导验证属性——因此可以覆盖仿真中无法穷举的 Corner Case。形式验证主要包括两大类：**属性检查/模型检查**（Property Checking / Model Checking）和**等价性检查（Equivalence Checking）**。

## 原理

### 模型检查（Model Checking）

模型检查是形式验证的核心算法。它将设计建模为一个有限状态转移系统（Kripke Structure），将验证属性表达为时序逻辑公式（Temporal Logic Formula，通常使用 SVA 或 PSL 表达），然后通过状态空间搜索算法验证该属性在整个状态空间中是否恒成立。如果属性不成立，模型检查器会生成一个**反例（Counterexample）**——一条从初始状态到达属性违反状态的精确路径，包含每一步的输入值和信号值，可以直接在仿真波形中重现。这一"反例即波形"的特性使得形式验证的调试效率极高：无需反复修改激励、运行仿真、检查波形，形式工具直接展示失败的确切路径。

模型检查的根本性挑战是**状态空间爆炸（State Space Explosion）**——$n$ 个触发器的状态数为 $2^n$，百万寄存器级设计的原始状态空间是天文数字（$2^{10^6}$）。控制复杂度的手段包括：抽象精炼（Abstraction Refinement）——对验证属性不相关的逻辑进行抽象简化；对称规约（Symmetry Reduction）——利用设计的结构对称性合并等价状态；组合推理（Compositional Reasoning）——将大设计分解为子模块独立验证；以及谓词抽象（Predicate Abstraction）——将具体的状态值归约为有限个谓词的真值组合。

### 时序属性分类与形式语义

形式验证中的属性按其时序特征分为两大类：

**安全属性（Safety Property）**——断言"坏的事情永远不会发生"，形式化为 $\mathbf{G}(\phi)$（全局恒成立）。典型例子包括：总线仲裁器不会同时授权两个 Master（`!grant[0] || !grant[1]`）、FIFO 不会上溢出、状态机不会进入未定义的死码状态。Safety Property 可以通过有限的反例（Finite Counterexample）证伪——如果属性违反，存在一条有限长度的路径到达违反状态。BMC 天然适合 Safety Property，因为只需要找到一个长度不超过 $k$ 的路径即可。

**活性属性（Liveness Property）**——断言"好的事情最终一定会发生"，形式化为 $\mathbf{GF}(\phi)$（无限频繁成立）或 $\mathbf{FG}(\phi)$（最终恒成立）。典型例子包括："每个请求最终一定会收到响应"、"仲裁器不会无限期饿死低优先级的 Master"。Liveness Property 的反证需要无限长的路径（Infinite Counterexample）——证明请求发出后响应永远不到达——这使得 BMC 无法完整证明或证伪 Liveness Property。活性属性的完整证明需要基于自动机理论的方法（如 Buechi Automata），或通过 Fairness Constraint（公平性约束）排除"理论上可能但实际不应考虑"的无限路径（例如"仲裁器永远给同一个 Master 授权"在公平性约束下被排除）。

**覆盖率属性（Cover Property）**——形式为 $\mathbf{EF}(\phi)$（存在一条路径使得属性成立），用于验证"目标场景是否可能被触达"。Cover Property 通常不以 SVA `assert` 形式出现，而是以 `cover property` 或形式工具的 Coverage Goal 形式表达。Cover Property 的可达性证明提供了一条精确的激励序列（Witness Trace），这条序列可以直接作为仿真激励或验证场景的参考，帮助验证工程师理解"在什么条件下这个 Corner Case 才会发生"。

### 有界模型检查（BMC）

有界模型检查（Bounded Model Checking, BMC）是一种实用的模型检查技术，它将验证范围限制在有限步数（Bound, $k$）内。BMC 将设计在 $k$ 个时钟周期内的展开逻辑转化为一个 SAT（布尔可满足性）或 SMT（可满足性模理论）问题——如果存在一条长度不超过 $k$ 的路径违反属性，SAT/SMT 求解器将找到它。

BMC 的优势在于：a) 对深度有限的设计（如流水线级数、总线超时计数器）可给出完整证明；b) 对浅层 Bug 的发现效率极高——大部分 RTL Bug 的可反例深度在几十个周期内。BMC 的局限性在于：a) 只能证明在 $k$ 步内没有违反，不保证 $k+1$ 步及以后；b) 对于需要无限深度才能证明的属性（如 Liveness Property，"请求最终一定会收到响应"），BMC 不能给出完整证明。**k-归纳**（k-Induction）是 BMC 的增强——通过证明 (a) 属性在最初 $k$ 步成立，且 (b) 如果属性在任意连续的 $k$ 步成立，那么第 $k+1$ 步也成立——从而将有限步证明推广为无限步证明。

### 等价性检查

等价性检查（Equivalence Checking）形式地证明两个设计表示之间的功能等价性，最经典的应用是 RTL-vs-Gate 等价性检查（Logic Equivalence Checking, LEC）。综合工具将 RTL 转换为门级网表，LEC 工具使用形式算法验证网表与 RTL 的输入输出行为是否在所有输入组合下完全一致。

LEC 的核心算法基于组合逻辑等价性：将 RTL 和网表的时序元件（触发器/寄存器/存储器）按名称或用户映射确认为比较点（Compare Points），然后将两端组合逻辑锥（Logic Cone）的布尔函数通过 SAT 求解器验证所有输出点（End Points）的布尔函数等价。如果存在不等价，LEC 输出导致差异的输入向量和对应的输出差异——类似于 Counterexample。对于 ECO（Engineering Change Order）阶段的手工网表修改，LEC 是确保修改不引入逻辑错误的标准验证手段。LEC 的 Compare Points 映射错误是最常见的等价性检查失败原因——RTL 的 `reg_a` 和网表的 `DFF_X1_a` 未正确对应时工具报告非等价，但实际上是映射问题而非设计问题。高级 LEC 工具（如 Cadence Conformal, Synopsys Formality）支持基于名称、拓扑、功能特征的自动映射和用户自定义映射规则（Mapping Rules），以处理综合工具的重命名和寄存器复制优化。

### 形式覆盖率

形式覆盖率（Formal Coverage）与仿真的功能覆盖率对应，但它衡量的不是"测试是否执行到了某场景"，而是"属性的覆盖范围"。形式工具自动分析设计中的可覆盖点（Coverable Points）——包括信号值、条件表达式、FSM 状态/弧——然后逐一检查这些点是否被已有属性集合约束到了具体值（Reachable）或仍可以取任意值（Unreachable Under Property Assumptions）。Unreachable 点表示现有属性没有对该信号施加任何约束——即验证存在"未被属性描述的盲区"。这一分析称为可达性分析（Reachability Analysis）或覆盖率不可达分析（Coverage Unreachability Analysis），用于评估形式属性集合本身是否完备。

### 形式验证的典型应用场景

形式验证在数字 IC 设计中的应用远不止属性检查。形式工具（如 Cadence JasperGold, Synopsys VC Formal, Siemens Questa Formal）提供了一系列"形式应用（Formal Apps）"——针对特定验证任务的预封装形式分析流程：

**连接性检查**（Connectivity Check）是形式验证最基本也最高效的应用——形式工具自动提取设计的信号连接拓扑，与用户定义的连接规范（通常是结构化表格或 SystemVerilog Property）进行比对，穷举地验证每一条指定连接在所有工作条件下是否确实连通。这在大型 SoC 的顶层连接验证（包括时钟网络、复位树、电源域交叉连接）中不可替代——仿真无法穷举所有信号状态的组合来检测连接错误。

**死锁与活锁检测**（Deadlock/Livelock Detection）利用形式验证的状态空间穷举能力，自动推导设计中可能导致系统永久停顿的状态环。工具分析 FSM 状态转移图，识别是否存在一类状态集合使得系统一旦进入就永远无法退出（死锁），或虽能退出但无法推进有效工作（活锁）。对于总线仲裁器、DMA 控制器、缓存一致性协议等涉及多 master 资源竞争的设计，死锁检测是形式验证的高价值应用。

**X-Propagation 分析**追踪设计中未初始化的 X 值是否可能传播到设计的关键输出（如复位信号、中断信号、数据有效标志）。形式工具通过从 RTL 寄存器（在复位解除时刻可能为 X）出发，分析所有可能的传播路径，判断 X 是否会到达输出端口并导致功能故障。X-Optimism/X-Pessimism 是 RTL-vs-Gate 仿真中 X 值行为不一致的根本原因——RTL 仿真的 X 传播语义是乐观的（某些情况下 X 被当 0/1 处理），而形式工具提供的 X-Prop 分析与实际硅片行为更接近。

**寄存器验证**（Register Verification）通过形式工具自动提取 Register Map 规范（IP-XACT, SystemRDL, CSV），生成对应的 SVA 属性集合，穷举地验证每一寄存器的复位值、读写属性、属性依赖关系和保留位行为。这比仿真的随机读写覆盖更彻底——形式工具保证每个 bit 都在所有可能的访问序列组合下被验证。

### 形式验证 vs 仿真

形式验证和仿真是互补而非替代关系。形式验证的优势在于穷举性——它用数学证明替代统计推断，适合属性检查（每个属性都被穷举证明或给出反例）、死锁/活锁检测（X-Propagation 分析）和边界条件的充分性验证。仿真的优势在于可扩展性——它对设计规模的敏感度远低于形式验证（形式验证的计算复杂度随状态空间指数增长），适合大规模 SoC 的系统级集成测试和性能验证。

工程实践中的典型分工是：a) 模块级（IP-Level）使用形式验证做属性证明和 Bug Hunting；b) 子系统级（Sub-System Level）二者结合——仿真做功能测试，形式做接口协议合规性检查；c) 芯片级（Chip-Level）以仿真为主，形式用于关键控制路径和寄存器配置序列的验证。"Bug Hunting"模式是形式验证的低成本入门方式——使用 `assert property (@(posedge clk) disable iff (rst_n) !(condition))` 搜索违反断言的路径而非证明断言恒成立，降低了计算复杂度。

## 关键要点

- **状态空间爆炸是形式验证根本挑战**：模型检查的状态空间爆炸是其根本性挑战——$n$ 个触发器的状态数为 $2^n$，需通过抽象精炼、对称规约和组合推理等技术控制复杂度
- **Assume-Guarantee 契约决定验证成败**：形式验证成功的关键是写好假设-断言契约（Assumption-Guarantee Contract）：输入假设（Assume）定义合法输入空间，输出断言（Assert）定义设计义务——错误的假设会导致"假装没有 bug"（False Positive）
- **Compare Points 映射是 LEC 失败主因**：LEC 的 Compare Points 映射错误是最常见的等价性检查失败原因——RTL 和网表的触发器名称或实例路径不匹配时报告不等价，实际上是映射问题
- **X-Propagation 是形式验证杀手级应用**：X-Propagation 分析是形式验证在数字设计中的杀手级应用——形式工具自动追踪 X 信号是否可能传播到设计的关键输出（触发复位、数据路径），检查 RTL 中复位和初始化的正确性
- **SVA 和 PSL 双重属性语言支持**：形式工具支持 SVA（SystemVerilog Assertions）和 PSL（Property Specification Language, IEEE 1850）作为属性规范语言，大多数形式工具同时支持二者
- **周转时间随复杂度差异极大**：形式验证的周转时间差异极大——简单属性检查可能几秒完成，复杂的端到端（End-to-End）证明可能需要数小时乃至数天——需要根据复杂度分类调度
- **Bug Hunting 模式降低计算复杂度**："Bug Hunting"模式降低计算复杂度——形式工具搜索属性违反而非证明属性恒成立，适用于初期设计缺陷爆发期
- **形式验证已进入主流 SoC 验证流程**：形式验证的成熟度已经从"安全关键领域的特殊工具"扩展到"主流 SoC 设计的标准验证组件"——主要驱动力是设计复杂度增长和形式工具的商业化成熟（JasperGold, VC Formal, Questa Formal）
- **ABV 实现一次编写两种验证**：断言驱动验证（Assertion-Based Verification, ABV）是形式与仿真的桥梁：同一组 SVA 属性既被仿真器在线检查（动态 ABV），也被形式工具离线证明（静态 ABV），实现"一次编写、两种验证"
- **求解引擎 BDD→SAT→SMT 四次跃升**：形式验证引擎的核心算法演进——从 BDD（二叉决策图）到 SAT（布尔可满足性）再到 SMT（可满足性模理论）——每次跃升都大幅扩展了可处理的设计规模，现代求解器可处理百万门级设计的属性检查
- **CUA 闭环迭代填补覆盖盲区**：覆盖率驱动的形式验证（Coverage-Driven Formal）是新兴范式——通过形式覆盖率不可达分析（Coverage Unreachability Analysis, CUA）自动识别验证盲区，生成新的 SVA 属性来填补覆盖空缺，形成"证明→分析→补属性→再证明"的闭环迭代
- **过约束是最常见的形式验证错误根源**：形式验证的假设-断言契约（Assume-Guarantee Contract）必须同时满足充分性（sufficient）和安全性（safe）：假设太强=假阳性（漏 real bug），假设太弱=假阴性（报告不存在的 bug——实际正确的行为被判定为违反）——过约束（Overconstraint）是最常见的形式验证错误根源
- **组合验证是扩展到大设计的关键方法**：组合验证（Compositional Verification）是将形式验证扩展到大型设计的关键方法——按模块边界分解全局属性为子属性，分别证明后再使用逻辑推断（如假设-保障推理）组合为全局证明
- **安全关键领域法规强制使用形式验证**：形式验证在安全关键领域的法规合规性要求——ISO 26262（汽车功能安全）和 DO-254（航空电子硬件设计保证）明确要求对 ASIL-D / DAL-A 级功能使用形式验证作为仿真和测试的补充
- **时间抽象缩减状态空间**：形式工具的时间抽象能力是处理复杂时序设计的关键——通过 Clock-Gating Abstraction 和 Reset Abstraction，形式工具可以忽略复位期间和时钟门控期间的不确定行为，显著缩小状态空间并避免在这些"无意义状态"上浪费求解资源
- **完备证明与有界证明 Signoff 权重须严格区分**：形式验证的"完备（Complete Proof）"和"非完备（Bounded Proof）"状态需要严格区分——完备证明（Proven）等于属性对所有深度的路径恒成立（通常要求 k-Induction 通过），有界证明（Bounded）仅保证在 b 个时钟周期内未找到反例，两者在 Signoff 审查中的权重完全不同

## 与其他概念的关系

- [[verification/concepts/SVA断言|SystemVerilog 断言（SVA）]] — SVA 属性是形式验证的第一公民输入语言，形式工具直接消费 `assert property`、`assume property` 和 `cover property` 语句作为证明目标、约束和覆盖率检查点，SVA 的 `##` 延迟运算符、`$past()`、`$rose()`/`$fell()` 等采样函数在形式工具中具有精确的形式语义定义
- [[verification/concepts/覆盖率模型|覆盖率模型]] — 形式覆盖率（Reachability Analysis）与仿真功能覆盖率互补：前者通过形式工具分析所有可覆盖点并报告未被属性约束的区域（Unreachable Under Properties），揭示属性集合的结构性盲区；后者通过随机激励统计测试是否触达了覆盖点，揭示测试激励的分布性盲区
- [[verification/concepts/验证平台架构|验证平台架构]] — 形式验证不需要 Testbench 的激励/监视器组件，但需要基于 Assumption 定义合法输入空间来替代 Testbench 的输入约束角色——Assumption 的质量直接等价于 Testbench 驱动的完整性，过弱或过强的 Assumption 分别导致假阴性和假阳性
- [[asic-flow/concepts/逻辑综合|逻辑综合（Synthesis）]] — LEC（逻辑等价性检查）是综合后 Signoff 的必选项，形式地证明综合优化（如寄存器重定时、资源共享、常量化简）未改变组合功能；对于物理综合引入的扫描链替换和多时钟域优化，LEC 需要额外的约束和映射文件（svf/upf）来指导等价性证明
- [[verification/concepts/UVM方法学|UVM 方法学]] — UVM 的仿真驱动验证与形式验证形成互补验证策略：UVM 适合数据路径吞吐和复杂业务场景的功能验证（随机激励的统计覆盖），形式验证适合控制路径的属性穷举证明、接口协议合规性检查和死锁/活锁检测（数学证明的逻辑保证），两者在模块级验证中共用 SVA 属性作为统一规范描述
