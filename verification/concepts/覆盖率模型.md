# 覆盖率模型

覆盖率模型（Coverage Model）是覆盖率驱动验证（Coverage-Driven Verification, CDV）方法论的核心组件，它用可量化的指标回答 "验证是否充分" 这一根本问题。在功能验证中，覆盖率分为两大类：**代码覆盖率（Code Coverage）** 和 **功能覆盖率（Functional Coverage）**。代码覆盖率由仿真工具自动收集，反映 RTL 代码的执行情况；功能覆盖率由验证工程师显式定义，描述测试计划中列出的功能点和场景是否被激励触发。两者缺一不可——代码覆盖率 100% 而功能覆盖率 0% 意味着所有代码都运行过但没有检验任何功能意图，反之亦然。

## 原理

### 代码覆盖率的四个维度

代码覆盖率是仿真器在运行时自动追踪并统计的指标，不需要用户编写额外的代码。

| 维度 | 统计内容 | 局限 |
|:---|:---|:---|
| **行覆盖率（Line）** | 每条可执行语句是否至少被执行过 | 执行过不等于逻辑正确 |
| **翻转覆盖率（Toggle）** | 每位信号是否经历过 0→1 和 1→0 | 不关联翻转的语义正确性 |
| **分支覆盖率（Branch）** | `if-else`/`case` 每个分支是否都被进入过 | 组合条件的子条件独立影响未区分 |
| **条件覆盖率（Condition）** | 组合条件中每个子条件对结果的影响是否都独立测试 | 仅存在于有 MC/DC 能力的工具中 |
| **FSM 覆盖率（FSM）** | 每个状态是否被访问、每条状态弧是否被遍历 | 仅覆盖显式状态机，不覆盖隐式状态 |

代码覆盖率是验证充分性的**必要条件但非充分条件**。一个典型反例：一个 ALU 的加法运算中，如果运算逻辑有 Bug 将 5+3 误算为 9 而非 8，代码覆盖率仍为 100%（加法器的所有行都被执行了），但功能是错误的。代码覆盖率不能替代功能覆盖率，但可以作为功能覆盖率模型的完整性检查——如果功能覆盖率声称已验证 "乘法" 操作但对应 RTL 代码的乘法路径行覆盖率为 0%，说明功能覆盖率采样位置有误。

### 功能覆盖率：Covergroup 结构

功能覆盖率由验证工程师通过 SystemVerilog 的 `covergroup` 结构显式定义。一个完整的 Covergroup 结构示例如下：

```systemverilog
// ===== Covergroup 功能覆盖率模型完整结构 =====
//
// covergroup: 功能覆盖率组关键字——声明一个覆盖率度量单元
//             类比：covergroup 相当于一个"功能点检查清单"
// cg_alu_ops: covergroup 名称（用户自定义，通常用 cg_ 前缀标识）
// @(posedge clk): 采样事件（Sampling Event）——指定何时触发采样
//                 每个 clk 上升沿，covergroup 检查信号值并更新覆盖率计数
covergroup cg_alu_ops @(posedge clk);
    // ===== 选项（Option）配置 =====
    // option: 实例级选项（每个 covergroup 实例独立配置）
    //   per_instance = 1: 每个实例独立统计覆盖率（默认 0 为所有实例合并统计）
    //                     UVM 环境中通常设为 1，以便区分不同 Agent 的覆盖率
    option.per_instance = 1;             // 各实例独立统计（不合并）

    //   goal = 95: 覆盖率目标阈值（百分比），用于自动化签核判断
    //              当此 covergroup 覆盖率达到 95% 时标记为"已达标"
    option.goal = 95;                    // 目标覆盖率 95%

    // type_option: 类型级选项（同一 covergroup 类型的所有实例共享）
    //   weight = 1: 在总体覆盖率加权平均计算中的权重
    //               设为 0 可将此 covergroup 排除在总体覆盖率之外
    //               关键 covergroup 建议权重 2-5 倍于辅助 covergroup
    type_option.weight = 1;              // 参与总体覆盖率计算（权重 1）

    // ===== Coverpoint 1：操作码分布 =====
    // coverpoint: 覆盖点关键字——定义对一个信号/表达式的覆盖率度量
    // cp_opcode: 覆盖点名称（用户自定义，通常用 cp_ 前缀标识）
    // alu_op: 被采样的目标信号（ALU 操作码），其值在每个采样事件时被捕获
    // bins: 分箱（Bucket）——将信号的值域划分为有意义的"桶"
    cp_opcode: coverpoint alu_op {
        // 显式分箱（Explicit Bins）：按功能语义手动分组
        bins add = {ADD};                // add 桶：仅包含 ADD 操作码值
        bins sub = {SUB};                // sub 桶：仅包含 SUB 操作码值
        bins mul = {MUL};                // mul 桶：仅包含 MUL 操作码值

        // logic_ops 桶：将 AND/OR/XOR/NOT 四种逻辑操作归入同一桶
        //   设计考量：如果四种逻辑操作共享相同的硬件路径，
        //   覆盖任意一种即可证明该路径已验证（不需要每种都单独覆盖）
        bins logic_ops = {AND, OR, XOR, NOT};

        // illegal_bins: 非法值桶——标记规范禁止出现的值
        //   如果仿真中 alu_op 取值为 5/6/7（非法操作码），仿真器立即报错
        //   这不是覆盖率排除机制，更是功能正确性检查机制（Checking + Coverage 双重职能）
        //   注意：非法操作码命中 → 仿真器报错（非警告），等同于断言失败
        illegal_bins reserved = {5, 6, 7};  // 保留操作码：命中即报错

        // ignore_bins: 忽略值桶——排除不关心的值域
        //   不计入覆盖率分子（命中次数），也不计入分母（总需命中次数）
        //   典型用途：排除保留字段、未实现功能、废弃操作码等
        ignore_bins unused = {15};           // 未使用操作码：不计入覆盖率
    }

    // ===== Coverpoint 2：操作数符号组合 =====
    // coverpoint 对象可以是复合表达式——此处连接两个信号的最高位
    // op_a[31]: 位选——取 op_a 的第 31 位（最高位，即符号位，0=正 1=负）
    // op_b[31]: 位选——取 op_b 的第 31 位（最高位，即符号位）
    // {op_a[31], op_b[31]}: 位拼接——组成 2-bit 的符号组合向量
    cp_sign: coverpoint {op_a[31], op_b[31]} {
        // 四种符号组合的显式分箱
        // 2'b00: 2-bit 二进制字面量——op_a 正 + op_b 正（正×正）
        bins pos_pos = {2'b00};
        // 2'b01: op_a 正 + op_b 负（正×负）
        bins pos_neg = {2'b01};
        // 2'b10: op_a 负 + op_b 正（负×正）
        bins neg_pos = {2'b10};
        // 2'b11: op_a 负 + op_b 负（负×负，结果应为正）
        bins neg_neg = {2'b11};
    }

    // ===== Cross 交叉覆盖率：操作码 × 符号组合 =====
    // cross: 交叉覆盖率——计算两个或多个 coverpoint 的笛卡尔积
    // cr_op_sign: 交叉覆盖率名称（通常用 cr_ 前缀标识）
    // cp_opcode, cp_sign: 参与交叉的两个覆盖点
    // 语义：检查 (操作码, 符号组合) 的每种组合是否都被激励到
    //   例如：ADD 操作 × 正正/正负/负正/负负 四个组合都必须被覆盖
    //   总 bin 数 = cp_opcode 的 bin 数 × cp_sign 的 bin 数 = 6 × 4 = 24
    cr_op_sign: cross cp_opcode, cp_sign;

// endgroup: covergroup 结束关键字（与 covergroup 配对）
endgroup
```

### Coverpoint 分箱（Bins）策略

`coverpoint` 通过 `bins` 将值域划分为有意义的桶（Bucket），分箱策略直接影响覆盖率模型的精确度和灵敏度：

- **自动分箱（`bins auto`）**：仿真器自动为每个可能的取值创建 bin。对 8-bit 信号产生 256 个 bin——适用于粗粒度的初步覆盖率采集，但缺乏语义分组
- **显式分箱（`bins name = {values}`）**：由用户按功能语义分组。例如将 `ADD` 和 `ADC`（带进位加）归入同一 bin、`SUB` 和 `SBC` 归入另一 bin——这样的分组使得覆盖率缺口直接映射回验证计划的功能点
- **非法分箱（`illegal_bins`）**：标记不允许出现的值，命中时仿真器报错。这不只是覆盖率排除机制，更是功能正确性检查机制
- **忽略分箱（`ignore_bins`）**：排除用户不关心的值域，不计入覆盖率分子和分母。常用于排除保留字段、未实现的操作码等

### 交叉覆盖率与 Bin 爆炸

`cross` 语法定义两个或多个 `coverpoint` 的笛卡尔积（Cartesian Product），用于捕捉多维功能空间中不同条件组合的覆盖情况。Cross 覆盖率是功能覆盖率中最强大也最危险的特性：

```systemverilog
// ===== Cross Bin 爆炸问题与防御策略 =====
//
// 交叉覆盖率的 bin 总数 = 各 coverpoint bin 数的乘积
// 不加控制的 cross 将导致 bin 数量爆炸——大量 bins 无法被覆盖且没有验证意义

// --- 反面案例：不加控制的交叉 ---
// 假设 cp_a/cp_b/cp_c 各 10 个 bin
// 三向交叉：10 × 10 × 10 = 1000 个 cross bins
// 问题：1000 个 bin 中绝大部分是不可达的（硬件不支持该组合）
//       覆盖率报告中将出现海量"未覆盖"bin → 无法区分真正遗漏 vs 语义无关
cr_all: cross cp_a, cp_b, cp_c;  // 危险！笛卡尔积爆炸（10×10×10=1000 bins）

// --- 正面案例：带 ignore_bins 过滤的选择性交叉 ---
cr_selective: cross cp_op, cp_addr {
    // auto_bins: 自动生成所有合法交叉 bin（与绑定的 cross 一致）
    // cross cp_op, cp_addr: 将两个 coverpoint 的 bins 做笛卡尔积
    bins auto_bins = cross cp_op, cp_addr;

    // ignore_bins ... with: 条件过滤语法——排除满足条件的交叉 bin
    //   cr_selective with (...): 引用当前 cross 内的 coverpoint 值
    //   cp_op == KERNEL_MODE: 引用 cp_op 覆盖点的当前 bin 取值
    //   &&: 逻辑与——两个条件同时成立才排除
    //   cp_addr inside {[0:4095]}: 地址值在 0-4095（用户空间低 4KB）范围内
    //   语义：内核模式 + 用户空间地址 → 规范禁止的组合 → 排除出覆盖率
    ignore_bins user_only = cr_selective with
        (cp_op == KERNEL_MODE && cp_addr inside {[0:4095]});
        //  操作码=内核模式      且  地址在用户空间     → 排除（不可达组合）
}
```

防止 Cross Bin 爆炸的策略：(1) 使用 `ignore_bins` 排除规范保证不可能出现的组合；(2) 使用 `binsof()` 在 cross 中施加条件过滤；(3) 将大 cross 拆分为多个小 cross，每个针对特定子场景；(4) 使用 `cross_auto_bin_max` 选项限制自动交叉 bin 的最大数量（通常设为 128 或 256）。

### 覆盖率收集的采样策略

Covergroup 必须通过 `sample()` 方法被显式触发，采样时机是覆盖率准确性的关键：

- **Monitor 采样**（推荐）：在 Monitor 的 `run_phase` 中，每收到一个事务（Transaction）调用 `sample()`。将覆盖率采样与观测层绑定，确保覆盖率反映的是 DUT 实际发生的行为
- **Interface 采样**：通过 `always @(posedge clk)` 在每个周期采样。适用于周期级精度的覆盖率需求（如流水线级间寄存器的值分布），但产生大量采样事件
- **Scoreboard 采样**：在 scoreboard 的比较逻辑中采样。适用于需要检查 DUT 内部计算结果准确性的覆盖率场景

`covergroup` 的关键选项：
- `option.per_instance = 1`：多个实例独立统计覆盖率
- `option.goal = 95`：覆盖率目标阈值
- `option.at_least = N`：每个 bin 至少命中 N 次才算 covered（默认 1，对随机性强的点建议 3-5）
- `type_option.weight = 0`：将该 covergroup 排除在总体覆盖率计算之外

### 覆盖率驱动验证（CDV）流程

CDV 流程是一个迭代闭环模型：

1. **验证计划（vPlan）**：将设计规范分解为可测试的功能点，每个功能点对应一个或多个 coverpoint/bin
2. **Covergroup 编码**：根据 vPlan 编写覆盖率模型，确保 vPlan 到 bin 的映射完整且无冗余
3. **回归运行**：运行多种子、多测试的回归仿真，收集覆盖率数据
4. **覆盖率分析**：使用覆盖率合并工具（URG/IMC/vManager）聚合数据，识别覆盖率缺口（Coverage Hole）
5. **约束调整**：根据缺口调整随机约束参数或编写定向测试（Directed Test）以覆盖特定组合
6. **重新运行**：迭代步骤 3-5，直到覆盖率收敛到目标

覆盖率收敛的典型曲线：无偏随机快速覆盖 70-80%（低悬果实），约束调整再覆盖 80-95%（需要针对性引导），定向测试填补最后 5%（极其冷门的 corner case）。

### 覆盖率合并与分级管理

覆盖率合并（Coverage Merge）是 CDV 的基础操作：将多次回归运行（不同随机种子、不同测试用例、不同配置参数）的覆盖率数据合并，生成总体验证覆盖视图。覆盖率分级管理在多层级验证中尤为重要：IP 级覆盖率必须达到 100%（所有 feature 在 IP 级被独立验证），子系统级覆盖率补充跨 IP 交互的覆盖率，芯片级覆盖率验证集成场景。

## 关键要点

- **双 100% 覆盖率不等于验证完成**：代码覆盖率 100% + 功能覆盖率 100% 不代表验证完成——还需验证覆盖率模型本身是完整的：vPlan 中的所有测试点都已映射到 coverpoint，且 bin 划分粒度合理
- **`illegal_bins` 兼具 Coverage 和 Checking 双职能**：`illegal_bins` 命中即报错——这使得 Covergroup 不仅是覆盖率度量工具，也是功能检查工具，兼具 Coverage 和 Checking 双重职能
- **Transition bins 捕获值转移比静态 bin 更有信息量**：Transition bins 语法 `bins t1 = (3'b000 => 3'b010)` 用于捕获信号的值转移覆盖——验证 FSM 状态转移路径或总线协议的事务序列时比静态值 bin 更有信息量
- **`cross_auto_bin_max` 防止交叉 bin 爆炸**：`cross_auto_bin_max` 选项限制自动交叉 bin 的数量上限（通常设为 128 或 256），超过上限时工具发出警告，提示用户需要显式管理交叉 bin
- **`get_coverage()` 支持运行时动态调整激励**：`get_coverage()` 方法返回 0-100 的实时覆盖率百分比，配合仿真时间回调可实现 Run-Time Coverage Closure——在仿真运行中动态调整激励策略
- **关键 Covergroup 加权提升指标准确度**：加权平均覆盖率（Weighted Average Coverage）中，关键功能点的 Covergroup 权重设为 2-5 倍于辅助 Covergroup，使总覆盖率指标更准确地反映验证健康度
- **Covergroup 代码量应为 DUT 的 20-40%**：覆盖率模型也有代码质量要求：Covergroup 代码量通常为 DUT RTL 代码量的 20-40%，过多暗示过度细化（Over-Specification），过少则覆盖不足
- **覆盖率评审是 Signoff 必经环节**：覆盖率评审（Coverage Review）是验证 Signoff 的必经环节——验证经理与设计经理一起审查覆盖率数据库，确认每个 Uncovered Bin 是否属于合法豁免（Waiver）还是真正遗漏

## 面试常见问答

### Q3: 什么是覆盖率？代码覆盖率和功能覆盖率的区别？

覆盖率（Coverage）是衡量验证充分性的量化指标。它将抽象的 "验证是否足够" 转化为可度量的数字——覆盖率 100% 是所有验证工程师的目标，但这只是验证完成的**必要条件而并非充分条件**。

**代码覆盖率（Code Coverage, CC）：自动收集的 "代码被执行过吗"**

代码覆盖率由仿真器自动追踪，不需要用户编写额外代码。它回答的问题是：RTL 代码的每行、每个分支、每个条件是否至少被执行过一次？

代码覆盖率的五个维度在前面原理部分已详述：行覆盖率（Line）、翻转覆盖率（Toggle）、分支覆盖率（Branch）、条件覆盖率（Condition）、FSM 覆盖率和表达式覆盖率（Expression）。

**代码覆盖率没到 100% 的常见原因：**

| 原因 | 说明 | 处理方式 |
|:---|:---|:---|
| **冗余代码** | RTL 中存在不可达的死代码（Dead Code）——如 `default: begin end` 从不执行 | 与设计者确认后删除或豁免（Waive） |
| **防御性代码** | 为安全性/可靠性添加的"理论上不可能出现"的条件分支 | 豁免——设计意图是合理的防御性编程 |
| **激励不足** | 测试激励未覆盖某些输入组合，导致部分代码路径未被触发 | 补充约束随机范围或编写定向测试 |
| **配置未覆盖** | 参数化 IP 的某些配置模式未在所有参数取值下验证 | 增加不同参数配置的回归测试 |
| **仿真工具限制** | 特定条件下的覆盖点（如 X 态传播路径）在某些仿真器中无法触发 | 与设计者确认后豁免 |
| **缺少特定场景** | 错误处理、异常路径、中断嵌套、低功耗状态切换等冷门场景未测试 | 编写专门的异常测试序列 |

**功能覆盖率（Functional Coverage, FC）：验证工程师定义的 "功能点被测试过吗"**

功能覆盖率需要验证工程师通过 SystemVerilog 的 `covergroup` 结构显式定义。它回答的问题是：验证计划中列出的每项功能、每个场景是否被激励触发过？功能覆盖率是将验证计划（vPlan）映射为可度量指标的过程。

**代码覆盖率 vs 功能覆盖率的本质差异：**

| 维度 | 代码覆盖率 | 功能覆盖率 |
|:---|:---|:---|
| **谁定义** | 仿真器自动收集 | 验证工程师手动编码 |
| **回答的问题** | "代码被执行过吗？" | "功能被验证过吗？" |
| **100% 的意义** | 所有代码行/分支都执行过 | 测试计划中所有功能点都覆盖到 |
| **100% 后还需做什么** | 不等于功能正确——每行都跑过，但逻辑可能是错的 | 不等于验证完成——覆盖率模型本身可能不完整 |
| **典型盲区** | 5+3=9（算错但仍达100%行覆盖） | 未定义 covergroup 的功能点完全没有体现 |

**覆盖率和断言覆盖率的关系：**

断言覆盖率（Assertion Coverage）通过 `cover property` 语句收集，属于功能覆盖率的子集：
- **`cover property`**：检查某个时序属性是否至少匹配过一次（"这个时序场景出现过吗？"）
- **Covergroup**：统计信号/事务的取值分布（"所有操作码都被使用过吗？所有交叉组合都被覆盖过吗？"）
- 两者互补——`cover property` 擅长时序模式可达性检查，Covergroup 擅长值域分布统计

**覆盖率和 Code-Driven Verification (CDV)：**

覆盖率驱动验证（Coverage-Driven Verification, CDV）是一个迭代闭环：
1. 根据 vPlan 编写 Covergroup
2. 运行随机回归收集覆盖率
3. 分析覆盖率报告，识别覆盖盲区（Coverage Holes）
4. 调整随机约束或编写定向测试填补盲区
5. 重新运行，迭代直到覆盖率收敛到目标

**功能覆盖率 Bins 分类策略：**

| Bin 类型 | 语法 | 作用 | 对覆盖率的影响 |
|:---|:---|:---|:---|
| **普通 bins** | `bins name = {values};` | 定义需要覆盖的值或范围 | 计入分子和分母——未命中降低覆盖率 |
| **`illegal_bins`** | `illegal_bins name = {values};` | 标记规范禁止的值 | 命中的仿真立即报错——兼具检查和覆盖率双重职能 |
| **`ignore_bins`** | `ignore_bins name = {values};` | 排除不关心的值域 | 不计入分子、不计入分母——完全隐藏在覆盖率报告之外 |
| **Transition bins** | `bins t = (A => B);` | 覆盖值转移路径 | 比静态值 bin 更有信息量——验证状态机的转移弧 |
| **Wildcard bins** | `wildcard bins w = {4'b00??};` | 通配符匹配多个值 | 适用于部分位不关心的场景（如只关心高两位） |

**覆盖率和 holes（覆盖率空洞）：**

覆盖率和 holes（Coverage Holes）是覆盖率报告中的 "未命中" bin——定义了但从未被激励覆盖到的功能组合。Holes 分析是 CDV 迭代的核心驱动力：
- **红线 holes**：vPlan 明确要求覆盖但从未命中 → 必须填补
- **灰线 holes**：不可达组合（如非法操作码组合）→ 应使用 `illegal_bins` 标记，不应显示为 holes
- **黄线 holes**：理论上可能但概率极低的 corner case → 可能需要定向测试

## 与其他概念的关系

- [[verification/concepts/约束随机验证|约束随机验证（CRV）]] — Covergroup 定义 "验证什么"，约束随机引擎定义 "激励空间"，两者通过覆盖率缺口反馈驱动约束迭代收敛，构成 CDV 的闭环核心
- [[verification/concepts/UVM方法学|UVM 验证方法学]] — UVM Monitor/Scoreboard 是 Covergroup 采样的标准位置，RAL 内建寄存器域覆盖率，`uvm_subscriber` 提供标准化的覆盖率收集接口
- [[verification/concepts/验证平台架构|验证平台架构（Testbench Architecture）]] — 覆盖率采样集成在 Monitor（观测 DUT 外部信号）和 Scoreboard（检查内部正确性），回归报告汇总覆盖率收敛仪表盘
- [[verification/concepts/SVA断言|SystemVerilog 断言（SVA）]] — `cover property` 提供基于属性的覆盖率，与 Covergroup 的结构化覆盖率互补，共同构成完整的可观测性
