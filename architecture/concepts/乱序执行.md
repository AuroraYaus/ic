# 乱序执行

乱序执行是现代高性能处理器实现指令级并行的核心技术。与顺序流水线不同，乱序执行允许指令在不违反程序语义的前提下以与程序顺序不同的次序执行——指令一旦操作数就绪即可发射执行，不再受前面无关指令阻塞的影响。这一机制将处理器的有效执行窗口从顺序流水线的几级扩展到数百条指令，大幅提升后端功能单元利用率。

## 原理

### Tomasulo 算法与保留站

Tomasulo 算法是乱序执行的基础框架，最早在 IBM System/360 Model 91 中实现。其核心机制：保留站作为功能单元的指令缓冲队列，每条指令在发射时被分配到对应功能单元的保留站条目中。源操作数通过标签传递——当操作数尚未计算完成时，保留站中记录的是产生该操作数的保留站编号而非寄存器号，一旦结果广播到公共数据总线（Common Data Bus, CDB），所有等待该结果的保留站同时捕获数据。这种寄存器重命名早期形式消除了 WAR 和 WAW 伪冒险。

### 寄存器重命名与重排序缓冲区

现代乱序执行处理器将 Tomasulo 的重命名机制系统化为物理寄存器文件和重命名寄存器映射表（Register Alias Table, RAT）。在译码后的重命名阶段，每条目的寄存器被分配一个空闲的物理寄存器（从 Free List 获取），RAT 维护架构寄存器到物理寄存器的映射关系。读端口通过 RAT 获取操作数对应的最新物理寄存器号，写端口通过分配新的物理寄存器消除 WAR/WAW——每条写操作写入独立物理寄存器，后续读取总是看到正确的最新值。

重排序缓冲区（Reorder Buffer, ROB）按程序顺序记录所有飞行中的指令信息：指令类型（ALU/Load/Store/Branch）、目标架构寄存器号、结果值和完成状态（Done Bit）。ROB 的提交阶段从其头部按序弹出指令：如果指令已完成则写回结果并弹出；如果未完成则流水线在 ROB 头部阻塞。ROB 支持精确异常：异常发生时只需标记 ROB 中对应条目的异常状态，提交时在异常指令处停止，其后的 ROB 条目全部清空——程序状态精确回退到异常指令执行之前。

### 发射队列与唤醒-选择循环

指令完成重命名和分配后进入发射队列。每个条目持续监控源操作数的就绪状态——每个源操作数对应一个 Ready 位。每个时钟周期执行：唤醒阶段——扫描所有条目，将 CDB 上广播的结果标签与条目源操作数标签通过 CAM 比较，匹配时标记操作数为就绪；选择阶段——从所有操作数就绪的指令中选取若干条发射到功能单元，通常按最老优先策略。唤醒-选择是乱序处理器中最关键的时序路径，随着发射队列增大 CAM 比较器网络开销平方增长，实际设计中使用分簇或分布式调度来管理时序。

### 访存排序与存储队列

Load-Store Queue（LSQ）负责维护访存指令的顺序语义。Load 指令在发出前必须检查 LSQ 中所有前序 Store 指令：如果存在地址匹配的前序 Store 且数据已就绪，则通过 Store-to-Load Forwarding 直接从 LSQ 获取数据；如果存在地址未确定的前序 Store，Load 必须等待地址确定（Memory Disambiguation）。Store 指令在提交阶段才真正写入 L1 D-Cache——保证了 Store 操作的不可逆性，错误路径上的 Store 不会污染内存系统。

### 分支误预测恢复

分支误预测恢复是乱序执行中最昂贵的操作。当分支指令在 EX 阶段确定实际方向与预测不一致时，处理器需要：刷新 ROB 中该分支之后的所有指令；将 RAT 恢复到分支时刻的映射状态（通过分支检查点快照机制）；回收被错误指令占用的物理寄存器；清空发射队列中错误路径的指令。恢复的时钟周期开销（通常 10-30 周期）直接构成有效误预测惩罚。

### 物理寄存器文件设计

物理寄存器文件（Physical Register File, PRF）是乱序执行的数据中枢。PRF 的端口数（读写端口数量）决定了每周期可以发射和提交的最大指令数：对于 W 宽度的发射，至少需要 2W 个读端口（每条指令最多两个源操作数）；对于 C 宽度的提交，至少需要 C 个写端口（每条提交的指令将一个结果写入 PRF）。总端口数 = 2W + C。

多端口 SRAM 的面积和功耗随端口数平方增长。实际设计中使用分簇策略：将 PRF 划分为多个物理体，每个体有独立的读写端口；或使用寄存器文件复制（Replication），每个功能单元簇拥有 PRF 的独立副本，通过广播机制维护跨副本的一致性。后一种方案在 Intel Core 的 Clustered Microarchitecture 中被采用——两个核心簇各自拥有独立的 PRF 和发射队列，通过簇间通信总线交换数据。

### 内存依赖预测与投机 Load

Load 指令在乱序执行中面临与 Store 指令的依赖不确定性。前序 Store 的地址尚未确定时，Load 无法确定是否可以安全地执行（是否与某条前序 Store 存在地址冲突）。内存依赖预测器（Memory Dependence Predictor）学习 Load-Store 对的冲突历史：如果历史上某 Load 和某 Store 频繁冲突，预测器标记该 Load 为 Speculative——允许 Load 投机执行但将其结果标记为投机性；当冲突的 Store 地址确定后，验证 Load 的正确性。如果 Load 投机正确，无额外开销；如果错误，Load 及其后续依赖指令需要从该点重放（Replay）。重放机制对性能的影响显著——高冲突率的 Load 频繁触发重放导致性能退化。

### 乱序执行的实际限制

虽然乱序执行理论上可以提取无限的 ILP（只要指令窗口足够大），实际性能受多种因素限制。指令窗口（ROB + 发射队列）的大小是核心约束——更大的窗口可以覆盖更多的独立指令，但窗口增大的代价是面积和功耗的平方到立方增长（CAM 比较器、物理寄存器文件端口等）。实际设计中窗口大小在 200-500 指令之间——这是面积、功耗和性能的三维帕累托最优前沿。

另一种限制是分支误预测——每次误预测清空窗口中的所有投机指令，相当于窗口的有效利用率下降。如果误预测率为 3% 且分支频率为 20%，平均每执行 100 条指令就产生约 3 × 0.2 = 0.6 次误预测。如果每次误预测清空平均 100 条指令，那么约 60% 的指令是"无效投机"——虽然硬件在执行它们，但结果永远不会被提交。这揭示了分支预测对乱序执行性能的决定性作用：提高预测精度不仅是减少暂停，更是增加前端向后端输送有效指令的效率。

### 乱序执行流水线的典型阶段划分

现代高性能乱序执行处理器的流水线按功能可划分为前端（Front-End）、中端（Mid-End / Issue）和后端（Back-End）三大阶段。前端负责将指令流入流水线：取指（IF）从 L1 I-Cache 取 16-32 字节的指令块，预译码（Pre-Decode）标记分支和指令边界，译码（Decode）将 ISA 指令分解为微操作（Micro-Operation, uOp），分支预测和 BTB/RAS 也在前端完成。中端是乱序执行的核心：寄存器重命名（Rename）通过 RAT 将架构寄存器映射到物理寄存器并分配 ROB 条目，分派（Dispatch）将 uOp 存入发射队列，发射（Issue / Wakeup-Select）在操作数就绪时将 uOp 送入功能单元。后端负责执行和提交：执行（Execute）由功能单元完成计算和访存，提交（Commit / Retire）从 ROB 头部按序将完成 uOp 的结果写入架构寄存器文件和内存。

流水线的深度与实际物理实现密切相关。在 Intel Golden Cove 微架构中，流水线深度约 14-16 级（从取指到执行），加上提交约 3-4 级，总计约 20 级。Apple Firestorm（M1 性能核）以更大的 ROB（约 630 条目）和更宽的发射宽度（8-wide）但更短的流水线（约 13 级）实现了极高的单线程性能和高能效比。这种"宽而浅"的设计哲学依赖于敏锐的预测器和充足的前端带宽来抵消浅流水线对预测精度的更高要求。

### Load-Hit-Store 与内存依赖性验证的硬件机制

当 Load 指令被投机发射而其前序 Store 的地址尚未确定时，Load 存在读错误数据的风险——如果 Store 的地址后来确定为与该 Load 相同且其数据已被更新。内存依赖性验证在 Store 地址确定后执行：将 Store 地址与所有在 ROB 中位于该 Store 之后但已被投机执行的 Load 的地址进行 CAM 比较。如果匹配（即 Load 错误地绕过了一个地址相同的 Store），则 Load 及其所有依赖指令必须从 ROB 中该 Load 点开始重放（Replay）。重放的代价不仅是 Load 本身的重新执行——所有消耗该 Load 结果的 ALU 指令也必须重新执行。大规模重放（Replay Storm）是性能杀手——一次 Load 重放可能触发连锁的数十条指令重放，当重放率超过 0.1% 时就开始出现可测量的性能退化。

### 面试题：什么是乱序执行（Out-of-Order Execution）？

乱序执行（Out-of-Order Execution, OoO）是现代高性能处理器的核心技术——它允许指令在不违反程序语义的前提下以与程序顺序不同的次序执行。在顺序流水线中，每条指令必须严格按程序顺序流经各级——如果指令 i 在 EX 阶段因为数据依赖而停顿，指令 i+1 即使操作数完全就绪也必须等待。乱序执行通过动态调度打破了这一限制：指令被译码并分配重排序缓冲区（Reorder Buffer, ROB）条目后进入发射队列，在发射队列中持续监控源操作数的就绪状态——操作数一旦就绪（前序指令结果已通过公共数据总线 CDB 广播），指令可立即发射到功能单元执行，无需等待前序无关指令完成。乱序执行将处理器的有效执行窗口从顺序流水线的几级扩展到数百条指令，大幅提升了功能单元的利用率——当一个功能单元被长延迟操作（如缓存缺失）阻塞时，其他功能单元仍可通过执行独立的后序指令来保续吞吐率。

乱序执行通过三大关键机制保证程序语义的正确性：(1) 寄存器重命名（Register Renaming）消除 WAR 和 WAW 伪冒险——每条写操作的架构目标寄存器被分配一个空闲的物理寄存器（从 Free List 获取），后续读取通过重命名映射表（Register Alias Table, RAT）查找到最新映射的物理寄存器。同一架构寄存器的多次写入对应不同的物理寄存器，WAR/WAW 在硬件层面完全消除。(2) 重排序缓冲区（Reorder Buffer, ROB）维护程序顺序的提交——所有飞行中指令在 ROB 中有固定条目，按程序顺序排列。指令在功能单元执行完成后在 ROB 中标记为 Done，但结果不写入架构寄存器文件（写入物理寄存器文件）。ROB 从头部按序提交——仅当头部条目为 Done 时提交该指令的结果到架构寄存器文件（将架构寄存器映射更新为该指令的物理寄存器），如果头部未完成则流水线在 ROB 头部阻塞。(3) Load-Store Queue（LSQ）维护访存指令的顺序语义——Store 指令在提交前不能真正写入 L1 D-Cache（Store 的不可逆性），投机执行的 Load 指令在 LSQ 中检查所有前序 Store 地址：如果地址匹配且数据就绪则通过 Store-to-Load Forwarding 获取数据（RAW 依赖的访存路径），如果存在地址未确定的前序 Store 则 Load 必须等待（内存消歧义）。

乱序执行相对于顺序流水线的性能提升是巨大的。以一个包含一次 L2 缓存缺失（约 15 个周期延迟）的代码序列为例：顺序流水线在缓存缺失期间整个流水线停顿 15 周期，后续即使有数百条与缺失无关的独立指令也无法执行。乱序执行下，不存在数据依赖的后续指令继续发射执行填充功能单元——当 ROB 窗口为 200 条时，缓存缺失期间可能有 100+ 条后续独立指令被发射执行。乱序执行的加速比受 ILP（Instruction-Level Parallelism）可用性的限制——典型标量程序（SPECint）每周期 ILP 在 1.5-2.5 之间，意味着 4 路乱序处理器的实际 IPC 通常 1.5-2.0（理想 IPC 为 4）。增加窗口大小可提取更多的 ILP 但收益递减——窗口从 128 扩大到 256 提升约 10-15% 的 IPC，从 256 扩大到 512 提升约 5-8%。

**关键要点：**
- **乱序执行打破顺序流水线的阻塞链**：指令一旦操作数就绪即可发射——前序指令的长延迟（如缓存缺失）不再阻塞后续独立指令的执行
- **Tomasulo 算法三大支柱**：保留站（RS，操作数就绪时发射）、公共数据总线（CDB，结果广播）、标签传递（替代静态寄存器号的动态标签）——WAR/WAW 通过标签传递而非物理寄存器重命名消除
- **ROB 提交保证程序的精确异常**：即使指令乱序执行，提交按程序顺序进行——异常在提交时处理，异常时刻的处理器状态等同于异常指令之前所有指令已完成、异常指令之后所有指令未执行
- **寄存器重命名是乱序执行的前提**：同一架构寄存器的多次写入映射到不同物理寄存器，消除写后写（WAW）和读后写（WAR）伪冒险——物理寄存器数量（通常 150-200）决定了重命名的容量上限
- **LSQ 是访存顺序的守门人**：Store 提交前不可写入缓存（不可逆），Load 需检查前序 Store 地址——Store-to-Load Forwarding 处理 RAW 访存依赖
- **分支误预测是乱序执行的阿喀琉斯之踵**：误预测导致 ROB 中错误路径的所有指令作废——误预测率 3% + 分支频率 20% → 约 60% 投机执行的指令被浪费
- **ROB 窗口大小决定 ILP 提取上限**：窗口越大可搜索的独立指令越多——典型高性能处理器 200-500 条目，Apple M1 约 630 条目，Intel Golden Cove 512 条目

### 面试题：什么是超标量（Superscalar）架构？

超标量（Superscalar）架构是指处理器在每个时钟周期内可以同时发射、执行和提交多条指令的微架构设计。标量（Scalar）流水线每周期发射 1 条指令，CPI 的最低值是 1.0；N 路超标量每周期发射 N 条指令，CPI 的理论最低值是 1/N。例如 4 路超标量处理器的理想 IPC 为 4.0。超标量的理论基础是指令级并行（Instruction-Level Parallelism, ILP）——程序中存在大量不互相依赖的指令，这些独立指令可以在同一周期内并行执行而不违反程序语义。超标量通过在流水线的关键阶段（取指、译码/重命名、发射、提交）并行处理多条指令来提取 ILP。

超标量引入了顺序流水线没有的核心微架构结构：(1) 宽取指——每个周期从 I-Cache 取出多个指令字（如 16-32 字节块，包含 4-8 条 32 位 RISC 指令），取指宽度决定超标量宽度的物理上限。(2) 并行译码和重命名——译码器每周期处理多条指令并检查指令间的依赖关系（交叉依赖检查），重命名阶段需要分配多个物理寄存器和多个 ROB 条目，RAT 每周期支持多个读端口（读取源操作数的最新物理寄存器映射）和多个写端口（更新目标寄存器的映射）。这些多端口结构（如 RAT 和 Free List）的面积和功耗随发射宽度平方增长——这是超标量宽度扩展的核心物理限制。(3) 多发射和多功能单元——发射队列每周期选择多条操作数就绪的指令发射到功能单元。后端必须配置足够的功能单元：N 路超标量通常配置 N 个简单 ALU、N/2 个复杂 ALU（乘法/除法）、N/2 个 AGU（地址生成单元/Load-Store 单元）、N/4 个分支单元。(4) 宽提交——ROB 头部每周期可提交多条已完成指令，写回架构寄存器文件，更新内存。

超标量与乱序执行通常组合使用——实际上几乎所有超标量处理器（自 Intel Pentium Pro 以来）都是乱序超标量设计。超标量提供宽度（每周期多条指令），乱序执行提供深度（在窗口中搜索独立指令）。两者的协同使处理器后端功能单元始终保持高利用率。超标量的实际加速比受程序 ILP 的限制——由于数据依赖、控制依赖和访存延迟，典型整数程序的 ILP 在 1.5-2.5 之间，这意味着 4 路超标量的实际 IPC 通常仅 1.5-2.0，远低于理想值 4.0。超标量宽度增至 6-8 路后，性能提升急剧递减——这是因为程序中相邻指令间的依赖链限制了每个周期可找到的独立指令数。

**关键要点：**
- **N 路超标量每周期发射 N 条指令**：理想 IPC = N，实际 IPC 受程序 ILP 限制——典型整数程序 IPC 仅 1.5-2.0（4 路超标量）或 2.0-3.0（6-8 路超标量）
- **宽取指和多端口结构是超标量的物理代价**：I-Cache 取指宽度、译码器并行度和 RAT 多端口数的面积随宽度平方增长——超过 8 路后面积代价超过性能收益
- **超标量和乱序执行协同工作**：超标量提供宽度（每周期多条指令的并行处理），乱序执行提供深度（在 200+ 指令窗口中搜索独立指令）——两者结合最大化功能单元利用率
- **交叉依赖检查限制超标量效率**：同一周期发射的两条相邻指令之间存在数据依赖时，其中一条必须被阻塞——这种"部分发射"降低了超标量宽度的有效利用率
- **超标量的分支误预测代价更高**：8 路误预测可能损失约 80-160 条投机指令（每周期 8 条 × 10-20 周期的误预测惩罚）——分支预测精度对宽超标量处理器至关重要
- **VLIW 是超标量的静态调度替代方案**：VLIW（Very Long Instruction Word）将多条指令打包为固定长度的指令束，由编译器而非硬件完成指令调度——简化硬件但需要重新编译且缺乏二进制兼容性
- **超标量宽度受 ILP 墙限制**：超过 4-6 路后 IPC 提升急剧递减——这是许多现代处理器将超标量宽度固定在 4-8 路的原因，进一步性能提升转向多核/多线程

## 关键要点

- **Tomasulo 核心创新是标签传递**：用标签传递代替寄存器号静态绑定，使 WAR 和 WAW 在硬件层面完全消除
- **RAT 映射生命周期**：每次重命名时创建新的架构到物理的映射，每次提交时释放老的物理寄存器，由 Free List 管理分配-释放生命周期
- **ROB 大小决定指令窗口上限**：决定飞行中指令数量上限，典型值 200-300+ 条（Apple M1 约 630 条，Intel Golden Cove 512 条）
- **唤醒-选择循环是关键路径**：CAM 匹配 N 个发射队列条目乘以 M 个 CDB 广播标签，规模和功耗显著增长
- **Store-to-Load Forwarding**：Load 必须从最近的前序 Store 获取数据，地址匹配优先于数据匹配，是 RAW 的关键解决路径
- **ROB 提交是存储可见性关卡**：Store 在 ROB 提交之前不能写入 L1 D-Cache
- **分支误预测 RAT 回滚机制**：带检查点维护最多 N 个分支时刻的快照（64-128 条），超过容量时较新分支暂停发射
- **PRF 端口数是宽度瓶颈**：N-wide 提交需要 N 个写端口，M-wide 发射至少需要 2M 个读端口
- **ILP 提取的代价巨大**：获取更宽 ILP 的代价是面积和功耗的平方到立方增长——发射队列越大 CAM 功耗越高
- **宽而浅 vs 窄而深设计哲学**：Apple M1（13 级 8-wide）和 Intel NetBurst（31 级 3-wide）代表两种设计哲学——前者靠大窗口提取 ILP，后者靠高频弥补窄发射
- **Load-Hit-Store 地址匹配**：Store 地址 CAM 与投机 Load 地址的比较逻辑决定了负载的最大投机激进程度，是 LSQ 的关键时序路径
- **ROB 提交速率即 IPC 上限**：提交速率 = Commit Width × Clock Frequency，是程序的最终可见 IPC 的上限——大于该速率的投机 ILP 提取都是浪费
- **PRF 分簇降低端口功耗**：将 PRF 分成 2-4 个体，跨簇传输通过簇间通信总线降低单个体的端口数和功耗
- **分支检查点保存 RAT 快照**：每遇到分支时保存 RAT 快照，误预测后恢复对应检查点的映射状态，典型实现维护 64-128 个检查点
- **唤醒-选择时序优化方案**：分簇发射队列（每簇独立 CAM）、并行 CAM 组（减少扇入扇出）和预测唤醒（推测操作数就绪，误预测时单周期气泡填充）
- **发射宽度决定后端并行度**：W-wide 发射需要至少 W 个 ALU、W/2 个 AGU（Load/Store 地址生成）、W/4 个分支执行单元和 W/4 个浮点/向量单元
- **LSQ 分裂为 LQ 和 SQ**：LQ 按 Load 的 ROB 顺序维护已投机执行的 Load 结果，SQ 按 Store 的 ROB 顺序维护提交前 Store 的数据和地址
- **uOp 融合减少窗口占用**：将两条相邻指令合并为单个 uOp——如 x86 的比较和跳转指令对融合为 Compare-and-Branch uOp，减少 ROB 和发射队列的占用
- **乱序执行面积占比高**：在 5nm 高性能核心中，ROB + 发射队列 + PRF + LSQ 的总面积可达核心总面积的 40-50%，其中发射队列因 CAM 结构占据最大份额

## 与其他概念的关系

- [[architecture/concepts/指令流水线|流水线（Pipelining）]] — 乱序执行是顺序流水线的进化版本，超标量在流水线基础上增加每周期发射宽度
- [[architecture/concepts/分支预测|分支预测（Branch Prediction）]] — 分支预测为乱序执行提供持续的投机指令流，预测精度直接决定 ROB 中有效工作量的比例
- [[architecture/concepts/存储层次|存储层次（Memory Hierarchy）]] — 非阻塞缓存和 MSHR 提供的 MLP 是乱序执行掩盖存储延迟的核心机制，MSHR 数量直接决定了 Load 缺失的并行容忍度
- [[architecture/concepts/缓存一致性|缓存一致性（Cache Coherence）]] — 多核乱序执行中，各核心的 Load/Store 提交顺序必须与内存一致性模型（TSO/Weak Ordering）匹配，ROB 提交顺序决定了向一致性协议暴露 Store 的时序
- [[architecture/concepts/指令集架构基础|指令集架构基础（ISA Fundamentals）]] — CISC 的变长指令和复杂编址模式使超标量的并行译码和交叉依赖检查更为复杂
