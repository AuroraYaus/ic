# 流水线设计

流水线（Pipeline）是提升数字电路吞吐率（Throughput）的核心微架构技术——将一个复杂的组合操作拆分为多个较短的阶段（Stage），相邻阶段之间插入流水线寄存器（Pipeline Register），使多个操作可以在不同阶段重叠执行，如同工厂装配线。流水线的核心权衡是：**吞吐率提升的代价是延迟（Latency）增加**（因寄存器插入的时钟周期开销）和面积/功耗增加（因流水线寄存器和握手逻辑的触发器开销）。流水线不仅用于处理器（经典的 5 级 RISC 流水线：取指-译码-执行-访存-写回），也是高性能算术单元（流水线乘法器、浮点加法器）、网络包处理器和图像处理管道的标准设计模式。

## 原理

### 吞吐率与延迟的权衡

流水线的性能指标由三个参数定义。**延迟（Latency）**：单个操作从进入流水线到完成的总时钟周期数，等于流水线级数 $N$。**吞吐率（Throughput）**：单位时间内完成的操作用数量——对于 $K$ 级流水线，理想吞吐率为每时钟周期 1 个操作（达到稳态后）。相比于非流水线的组合逻辑实现（吞吐率为 $1/K$ 每周期），流水线吞吐率提升 $K$ 倍。

关键公式：非流水线组合逻辑延迟 $T_D$ 被拆分为 $N$ 个阶段，每阶段延迟 $T_D/N$（理想均分），则最大时钟周期 $T_{clk} = T_D/N + T_{setup} + T_{clk2q}$，吞吐率 = $1/T_{clk}$。实际拆分中受制于逻辑单元的不均匀性——某些路径天然较长（如乘法器的进位链），均匀拆分需要额外组合逻辑平衡。

### 寄存器切片（Register Slicing）

寄存器切片是流水线化的基本操作——在组合逻辑中间插入寄存器以打断长路径。切片的艺术在于选择插入位置使各阶段延迟尽量均衡——如果某一阶段的逻辑深度是其他部分的 2 倍，则该阶段决定了整个流水线的时钟频率（最弱链路原理）。自动流水线化工具（如 Synopsys DC 的 `pipeline_design`）可在指定延迟预算的条件下自动分段插入寄存器，但手动切片通常产生更可预测的结构。

### Stall 和 Flush 协议

流水线必须在外部事件打断正常流时维护数据完整性。**Stall（停顿）**：当下游无法接收数据时（如缓存未命中、总线仲裁等待），流水线必须冻结所有阶段——将所有阶段寄存器使能关闭，保持当前数据不变。Stall 信号（通常为低电平有效的寄存器使能或时钟门控信号）从下游传播到上游，每一级在下一级准备好之前暂停。

**Flush（冲刷）**：当指令无效时（如分支预测失败、中断），必须清除流水线中已完成部分操作的无效数据——将对应阶段的 valid 位清零或直接将流水线寄存器设置为 NOP（No-Operation）编码。Flush 信号必须同时清除多个流水级的数据，需要确保不会误清除正在执行的有效操作。

Stall 和 Flush 是流水线控制器的两个核心原语——Stall 是"等待"，Flush 是"放弃"。两者在时序路径上的优先级需要明确定义：当 Stall 和 Flush 同时发生时，典型优先级是 Flush 优先（取消的操作不需要保存）。

### Valid-Ready 背压机制

Valid-Ready（或称 AXI-Stream 握手）是流水线间数据传输的标准接口协议。发送端驱动 `valid` 信号指示数据有效，接收端驱动 `ready` 信号指示可以接收。当 `valid && ready` 在同一时钟沿同时为真时，数据在发送端和接收端之间完成一次传输（Handshake）。如果接收端未就绪（ready=0），发送端必须保持 valid 和数据稳定——这就是背压（Backpressure）。

Valid-Ready 接口的正确实现需要考虑几个关键细节：a) ready 信号在流水线中必须可组合——`ready_stage_N = ready_stage_N+1 || !valid_stage_N+1`（下游有空位或数据未被占用的条件下拉高 ready）；b) 全流水线级联的 Valid-Ready 链从末端到前端的级别数决定了背压的传播延迟——过长的流水线可能需要在 ready 路径上插入寄存器（Skid Buffer）；c) valid 和 ready 的变化都必须在时钟沿被采样，避免组合环（Combinational Loop）。

### 转发（Forwarding）与数据冒险

流水线中的数据冒险（Data Hazard）发生在后续指令需要前面指令结果，但该结果尚未写入寄存器堆时。**转发**（Forwarding/Bypassing）通过 MUX 将从流水线后级（执行阶段输出、访存阶段输出）的计算结果直接旁路到前级（执行阶段输入），绕过寄存器堆写入再读取的延迟。转发将 RAW（Read-After-Write）冒险的处理周期从等待写回到寄存器堆的多周期减少到在流水线中插入 0-1 个气泡。转发的 MUX 增加了解码执行路径的组合逻辑延迟，需要仔细评估时序影响。

**结构冒险**（Structural Hazard）发生在两个操作同时竞争同一硬件资源时（如单端口寄存器堆的读端口数不足、除法器未流水线化）。解决方案包括：复制资源（增加读端口）、时分复用（Stall 一个操作等待资源空闲）、或架构避免（分离指令和数据缓存）。

### 流水线乘法器示例

以 16x16 位流水线乘法器为例展示流水线化技术。非流水线 Booth-Wallace 乘法器延迟约 $T_{booth} + T_{wallace\_tree} + T_{final\_adder}$。将其分为 3 级流水线：第一级（Booth 编码和部分积生成），第二级（Wallace 树压缩到两个部分和），第三级（最终加法器）。每级插入 32 位寄存器，三级流水线吞吐率达到每周期 1 次乘法，而非流水线版本约每 3 周期 1 次。面积开销约为三级寄存器（96 个 D-FF）加上必要的 Stall/Flush 控制逻辑（约 30-50 个等效门）。

### Skid Buffer 与反压传播延迟

当 Valid-Ready 流水线级数较长（>10 级）时，ready 信号从流水线末端逐级向前传播的组合路径可能成为新的时序瓶颈——每一级 ready 取决于下一级的 ready 和 valid 状态，形成 $\mathcal{O}(N)$ 的进位链式延迟。**Skid Buffer**（滑动缓冲）是解决长流水线反压传播延迟的标准技术——在 ready 路径上插入两级寄存器（Skid Buffer），将 ready 的传播延迟从组合路径转化为可时序约束的寄存器到寄存器路径。

Skid Buffer 的双寄存器结构：当接收端反压（ready=0）时，数据首先被缓存在第一个 Skid 寄存器中；如果反压持续，数据进一步被缓存到第二个 Skid 寄存器（两级深度的弹性缓冲区）。两级 Skid Buffer 允许 ready 信号在最坏情况下有 2 个周期的延迟（两级寄存器链的 clk2q + 组合逻辑），而非一长串组合逻辑的聚合延迟。Skid Buffer 的容量通常为 2（两级深度），足以覆盖绝大多数的流水线反压延迟需求——对于极端长的流水线（如网络包处理器的 32 级流水线），可在每 8-10 级之间插入一个 Skid Buffer 将 ready 路径分段。

**Skid Buffer 可综合实现的核心逻辑**：

```systemverilog
/**
 * skid_buffer: 两级滑动缓冲（Skid Buffer）
 *
 * 在 Valid-Ready 流水线中插入弹性缓冲级，解决反压（Backpressure）
 * ready 信号从下游逐级向前传播的长组合路径时序瓶颈问题。
 *
 * 工作原理（两级缓冲）：
 *   1. 正常模式（o_ready=1 或 o_valid=0）：输入数据直通到输出
 *   2. 反压模式（o_ready=0 且 o_valid=1）：输入数据暂存到 skid_data
 *   3. 恢复模式（反压解除后）：skid_data 中的缓存数据送回输出
 *
 * 关键设计意图：
 *   - 将 i_ready 设计为纯组合逻辑（assign），避免 i_ready 路径上
 *     的寄存器延迟累加到上游的反压传播链中
 *   - 两级缓冲允许下游反压持续 1-2 拍而不丢失数据
 *   - ready 信号从 O(N) 组合延迟变为可时序约束的寄存器到寄存器路径
 *
 * @param WIDTH  数据位宽（默认 32 位）
 *
 * @note  i_ready 为纯组合逻辑——反压信号无延迟穿透
 * @note  缓冲区深度为 2（o_valid 本身 + skid_data 一级）
 * @note  仅在 o_ready=0 且 o_valid=1 时启用 skid 存储
 * @see   [[rtl-design/concepts/流水线设计|流水线设计]]
 */
module skid_buffer #(parameter WIDTH = 32) (
    input  logic             clk,             // 时钟（上升沿有效）
    input  logic             rst_n,           // 复位（低电平有效）
    input  logic             i_valid,         // 上游数据有效标志
    input  logic [WIDTH-1:0] i_data,          // 上游输入数据（WIDTH 位宽）
    output logic             i_ready,         // 对上游的就绪标志（组合逻辑输出）
    output logic             o_valid,         // 对下游的有效标志（寄存器输出）
    output logic [WIDTH-1:0] o_data,          // 对下游的输出数据（寄存器输出）
    input  logic             o_ready          // 下游就绪标志
);
    // skid_data：弹性缓冲区——仅在反压期间暂存输入数据
    // WIDTH 位宽，与数据通路位宽一致
    logic [WIDTH-1:0] skid_data;
    // skid_valid：弹性缓冲区有效标志
    //   skid_valid=1 → skid_data 中有待发送的缓存数据
    //   skid_valid=0 → skid_data 为空
    logic             skid_valid;

    // ===== 组合逻辑：i_ready（上游反压信号）=====
    //
    // assign：连续赋值——i_ready 是纯组合信号，不经过寄存器
    //   这确保上游模块可以在同一时钟周期内看到 ready 变化，
    //   无需等待一个时钟周期的寄存器延迟
    //
    // o_ready || !o_valid || !skid_valid：只要满足以下条件之一，就可以接收新数据：
    //   - o_ready=1 → 下游可以接收，本模块输出即将被取走
    //   - !o_valid=1 → 输出寄存器空闲（o_valid=0），无数据等待送出
    //   - !skid_valid=1 → skid 缓冲区为空，可接收数据暂存到 skid
    //   逻辑或（||）：三种情况下均可接收——这是 Skid Buffer 的关键公式
    assign i_ready = o_ready || !o_valid || !skid_valid;

    // ===== 时序逻辑：输出寄存器与弹性缓冲控制 =====
    //
    // always_ff @(posedge clk or negedge rst_n)：异步复位的时序块
    //   - posedge clk：时钟上升沿采样
    //   - negedge rst_n：异步复位——rst_n 下降沿立即复位
    //
    // 数据流动的三种场景：
    //   场景 A: i_ready=1, o_ready=1 (或 o_valid=0)
    //           → 数据直通：i_data → o_data，o_valid ← i_valid
    //   场景 B: i_ready=1, o_ready=0 且 o_valid=1 (下游反压)
    //           → 数据缓存：i_data → skid_data，skid_valid ← i_valid
    //   场景 C: o_ready=1, skid_valid=1 (反压解除)
    //           → 恢复发送：skid_data → o_data，o_valid ← 1，skid_valid ← 0
    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            o_valid    <= 1'b0;               // 复位：输出无效
            skid_valid <= 1'b0;               // 复位：弹性缓冲区空
        end else begin
            // ----- 接收端逻辑：上游数据到达时 -----
            // i_ready=1 表示可以接收上游数据
            if (i_ready) begin
                // 子条件 1：输出端空闲（场景 A——数据直通）
                //   o_ready=1 → 下游可以取走当前输出
                //   !o_valid=1 → 输出寄存器为空，无旧数据
                //   两者满足任一即可直接将数据送到输出
                if (o_ready || !o_valid) begin
                    o_valid <= i_valid;       // 传递有效标志到输出
                    o_data  <= i_data;        // 传递数据到输出
                // 子条件 2：输出端繁忙且非空（场景 B——反压缓存）
                //   o_ready=0 且 o_valid=1 → 输出被占用，下游不接受
                //   将新数据暂存到弹性缓冲区 skid_data
                end else begin
                    skid_valid <= i_valid;    // 标记弹性缓冲区有效
                    skid_data  <= i_data;     // 暂存数据到弹性缓冲区
                end
            end
            // ----- 发送端逻辑：反压解除后恢复发送 -----
            // o_ready=1：下游准备就绪
            // skid_valid=1：弹性缓冲区中有待发送的缓存数据（场景 C）
            //   将缓存数据发送到输出，清空弹性缓冲区
            if (o_ready && skid_valid) begin
                o_valid    <= 1'b1;           // 输出变为有效
                o_data     <= skid_data;      // 发送缓存的数据
                skid_valid <= 1'b0;           // 清空弹性缓冲区
            end
        end
    end
endmodule
```

### 流水线的代价与收益

流水线的本质是用**面积换吞吐率**、用**延迟换频率**，其损益分析可精确量化。

**收益（Benefits）**：
- **吞吐率线性提升**：$K$ 级理想流水线的吞吐率约为非流水线版本的 $K$ 倍（达到稳态后每周期完成 1 个操作）。
- **时钟频率提升**：每级组合逻辑深度降低到原来的约 $1/K$，关键路径缩短使 $f_{max}$ 提升——这是流水线最直接的价值。
- **面积效率**：虽然流水线寄存器增加了面积，但综合工具可以用更小的门驱动更短的路径，部分抵消面积开销。

**代价（Costs）**：
- **延迟（Latency）增加**：单个操作从输入到输出经历 $K$ 个时钟周期（vs 非流水线的 1 周期），对于延迟敏感的控制路径（如中断响应）不可接受。
- **流水线寄存器面积**：每级插入位宽为 $W$ 的寄存器组，$K-1$ 级流水线增加的 DFF 数量 = $(K-1) \times W$。对于 64 位数据路径的 5 级流水线，仅数据寄存器就增加 256 个 DFF。
- **控制复杂度**：Stall、Flush、转发、冒险检测等控制逻辑的 RTL 代码量和验证复杂度随流水线深度增加而增长。
- **功耗增加**：更多 DFF 意味着更多时钟树负载和翻转功耗。但时钟门控可以部分补偿（Stall 期间停止翻转）。

### 理想加速比与实际效率

**理想加速比**（Ideal Speedup）：假设组合逻辑可以完全均匀分割，$K$ 级流水线的理想加速比为 $K$——即吞吐率是非流水线的 $K$ 倍。公式：$\text{Speedup}_{\text{ideal}} = K$。但这个假设在现实中不成立。

**实际加速比**受限于三个因素：

1. **逻辑不平衡（Logic Imbalance）**：组合逻辑无法均匀分割——乘法器的 Booth 编码和 Wallace 树天然有不同的逻辑深度。如果最慢阶段的延迟为 $T_{max}$，则 $T_{clk} \geq T_{max} + T_{setup} + T_{clk2q}$，加速比降至 $\frac{T_{comb}}{T_{max} + T_{ovhd}}$，其中 $T_{ovhd}$ 为寄存器开销。

2. **寄存器开销（Register Overhead）**：每级 DFF 的 $T_{clk2q} + T_{setup}$ 约 50-150ps（28nm 工艺），这是一个固定的每级开销。公式：$T_{clk} = \max(T_{stage\_i}) + T_{clk2q} + T_{setup}$。当流水线级数过多时，寄存器开销总和可能超过组合逻辑延迟本身——即"过度流水线化"（Over-Pipelining）。

3. **气泡（Bubble）损失**：数据冒险和控制冒险导致流水线中插入气泡（空闲周期），实际吞吐率 = 理想吞吐率 $\times$ (1 - 气泡率)。分支预测失败是气泡的主要来源——预测失败率为 5% 时，12 级流水线损失约 40% 的峰值吞吐率。

**效率**（Efficiency）定义：$\eta = \frac{\text{实际吞吐率}}{\text{理想吞吐率}} = \frac{\text{有效操作数}}{\text{总周期数}}$。非流水线 $\eta = 1/K$（因为 $K$ 周期才完成一个操作，其余 $K-1$ 周期浪费）；流水线 $\eta \to 1$（气泡率趋近于 0 时）。

### 流水线深度选择

流水线深度（级数 $K$）的选择是系统级决策，需要在以下因素之间权衡：

1. **目标时钟频率**：$f_{target}$ 决定了每级的最大允许延迟——$T_{per\_stage} \leq \frac{1}{f_{target}} - T_{setup} - T_{clk2q}$。如果组合逻辑总延迟为 $T_{total}$，则 $K_{min} = \lceil \frac{T_{total}}{T_{per\_stage}} \rceil$。

2. **延迟预算**：如果系统规格要求最大延迟不超过 $L$ 个时钟周期，则 $K \leq L$——这对实时控制系统是硬约束。例如，中断响应延迟要求 < 5 周期，则中断处理流水线不能超过 5 级。

3. **面积约束**：每增加一级流水线增加 $W \times 1$ 的寄存器面积（$W$ 为数据位宽）加上控制逻辑。在面积紧张的设计中（如 IoT MCU），级数受限。

4. **功耗预算**：更多流水线级数 = 更多 DFF = 更高时钟树功耗。Stall 期间的时钟门控可以部分弥补，但不能完全抵消。

5. **物理设计反馈**：在深亚微米工艺中，流水线寄存器在版图中的物理位置必须靠近其所分隔的组合逻辑——过深的流水线使寄存器的物理分布面积增大，互连线延迟可能超过组合逻辑延迟。经验法则：当寄存器到寄存器的物理距离超过 200-300um（7nm/5nm 工艺），互连线 RC 延迟成为主导，与组合逻辑延迟可比。

**实践中的参考值**：处理器微架构 5-15 级（Cortex-A 系列约 8-13 级，Intel Core 约 14-19 级）；乘法器/算术单元 2-5 级；网络包处理 3-10 级；图像处理管道 5-20 级。当单级延迟 < 8-10 个标准门延迟（FO4 延迟）时，寄存器开销开始主导——不建议继续深化。

### 流水线与超标量的区别

流水线（Pipelining）和超标量（Superscalar）是两种正交的并行技术，常常被混淆。核心区别：

| 维度 | 流水线 | 超标量 |
|:---|:---|:---|
| **并行维度** | 时间并行（Temporal）——不同操作重叠在不同阶段 | 空间并行（Spatial）——同一周期发射多条指令 |
| **硬件基础** | 阶段寄存器 + 阶段间旁路 | 多套执行单元（多 ALU、多 LSU、多 FPU） |
| **峰值 IPC** | 1（标量流水线） | >1（2-way = IPC 2，4-way = IPC 4） |
| **瓶颈** | 最慢阶段 | 指令级并行度（ILP）和依赖关系 |
| **控制复杂度** | Stall/Flush/Forwarding | 多发射逻辑、寄存器重命名、重排序缓冲 |

流水线是超标量的基础——超标量处理器内部每一套执行单元的路径通常也是流水线化的。然而，超标量的"超标"指的是**发射宽度**（Issue Width，每周期发射的指令数），而非流水线深度。一个 4-way 超标量 + 10 级流水线的处理器，每个时钟周期最多同时有 4 条指令分布在 10 个流水线阶段中。

### 流水线与乱序执行的关系

流水线和乱序执行（Out-of-Order Execution, OoO）解决不同层面的并行性问题：

- **流水线**解决的是**指令间的时间重叠**——不同指令的不同阶段同时运行，但指令按程序顺序（Program Order）开始和完成。这是**顺序流水线**（In-Order Pipeline）。
- **乱序执行**解决的是**数据依赖导致的流水线停顿**——当一条指令因数据依赖（如缓存未命中）无法继续时，后续无依赖的指令可以"越过"它先执行。乱序执行的核心硬件支撑是**寄存器重命名**（Register Renaming）消除假依赖（WAR/WAW）和**重排序缓冲区**（Reorder Buffer, ROB）管理指令的乱序发射和顺序提交。

两者的关系：**乱序执行是流水线的上层建筑**——流水线提供了时间并行的基本框架；乱序执行在这个框架上增加了动态调度能力，以容忍缓存未命中等长延迟事件。现代高性能处理器同时使用深度流水线（10-19 级）和乱序执行（ROB 深度 200-600 条指令），两者协同工作以实现高的指令级并行度。但乱序执行也引入了流水线中的**精确异常**（Precise Exception）处理难题——因为指令不再按程序顺序完成，发生异常时必须能回退到异常指令的精确状态。

## 关键要点

- **吞吐率提升以延迟和面积为代价**：吞吐率提升（$K$ 倍）以延迟增加（$K$ 周期）和寄存器面积/功耗为代价，流水线级数 $K$ 的选定是全系统时序和面积权衡的结果
- **均衡切片遵循最弱链路原则**：寄存器切片的最优位置是使各阶段延迟均衡，最长阶段决定整个流水线频率
- **Stall/Flush 为流水线控制核心原语**：Stall 冻结数据（等待），Flush 清除无效数据（放弃），同时发生时 Flush 优先
- **Valid-Ready 背压为级联标准接口**：ready 必须从下游到上游可组合传递，长流水线需考虑 ready 传播的时序收敛
- **转发是处理数据冒险的关键**：通过旁路 MUX 将后级结果直接馈入前级，将 RAW 冒险惩罚降至 0-1 个周期
- **结构冒险三种解决方式**：通过资源复制（多端口）、时分复用（Stall）或架构避免（分离 I-Cache/D-Cache）解决
- **流水线乘法器三段分割**：典型分割为 Booth 编码 -> 部分积压缩 -> 最终加法，每级寄存使得吞吐率达到每周期 1 次乘法
- **时钟门控降低 Stall 期间功耗**：Stall 期间各阶段输出数据不变，门控时钟消除无意义的触发器翻转
- **Skid Buffer 解决反压传播延迟**：两级弹性缓冲在 ready 路径上插入寄存器，将 $\mathcal{O}(N)$ 组合延迟转化为可约束的寄存器到寄存器路径
- **气泡率衡量流水线效率**：气泡（Bubble）是 Stall 或 Flush 导致的流水线空闲周期，分支预测失败是处理器流水线气泡的主要来源
- **寄存器物理布局影响时序收敛**：流水线寄存器需要物理上靠近其所分隔的组合逻辑块，物理分布直接影响时钟树延迟平衡和时序收敛的难度

## 与其他概念的关系

- [[rtl-design/concepts/时序逻辑|时序逻辑]] — 流水线寄存器本质是 D-FF，流水线最大频率由最慢阶段的 setup/clk2q 决定。时钟树平衡和寄存器物理布局直接影响流水线各阶段间的时钟偏斜（Clock Skew）预算分配
- [[rtl-design/concepts/有限状态机|FSM 设计]] — 流水线控制器（Stall/Flush 逻辑）本质上是 FSM+Datapath 分离设计的典型实例。FSM 的状态转换（如 IDLE -> ACTIVE -> STALL -> FLUSH）直接控制流水线寄存器的使能和清零
- [[rtl-design/concepts/算术电路|算术电路]] — 高性能算术单元（乘法器、加法器、除法器）广泛使用流水分割以提升吞吐率。乘法器从 Booth 编码到 Wallace 树到最终加法的三阶段分割是流水线在数据通路中最直接的应用
- [[architecture/concepts/指令流水线|体系结构流水线]] — 处理器级流水线与 RTL 级流水的接口对齐——处理器微架构决策（如指令发射宽度、重排序缓冲区深度）驱动 RTL 流水线的划分方式和握手协议设计
